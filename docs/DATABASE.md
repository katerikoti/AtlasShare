# AtlasShare — Database

Status: **planned.** No database exists yet. The schema below is the Phase 2
target and the contract later phases build on. It will be adjusted only with a
documented reason (and a migration), not silently.

## 1. Principles

1. **Postgres is the source of truth** for accounts, visits, memberships, and
   invitations. The country dataset is static application data, not a table.
2. **Every user-owned row is scoped by `userId`**, and every read/write goes
   through a server-side authorization helper. There is no "trusted client".
3. **Cascades are deliberate.** Deleting an account must remove that person's
   private data. Shared-map content owned by that person is deleted with it.
4. **Tokens are stored hashed.** Invitation tokens and Better Auth's internal
   secrets never appear in plaintext in the database or logs.
5. **Timestamps are UTC** (`timestamptz`), generated by the database or Prisma,
   never by the client.
6. **Country codes are ISO 3166-1 alpha-2**, uppercase, two characters, and
   validated against the committed dataset before insert.

## 2. Connection model

Neon provides two connection strings:

- `DATABASE_URL` — **pooled** connection, used by the app at runtime (Prisma
  Client with `@prisma/adapter-neon`).
- `DIRECT_URL` — **direct** connection, used only for migrations and
  introspection.

Prisma 7 is ESM and configured through `prisma.config.ts`; the CLI reads the
direct URL, the runtime client uses the pooled URL. Never point
`TEST_DATABASE_URL` at production.

Local development options (decide in Phase 2): a Neon branch, or a local
Postgres in Docker. Neon branches are preferred because they match production
semantics (including pooling and SSL).

## 3. Schema (planned)

The final Prisma schema will be generated for Better Auth first, then extended
with the application models below. Better Auth's generated schema is the source
of truth for its own tables — do not hand-edit those fields to "tidy" them.

### 3.1 Better Auth tables

Standard Better Auth Prisma models (names/fields must match the installed
version's generator output):

- **User** — `id`, `name`, `email` (unique), `emailVerified`, `image`,
  `createdAt`, `updatedAt`, plus AtlasShare additional fields:
  - `welcomeEmailSentAt DateTime?` — prevents duplicate welcome emails.
- **Session** — `id`, `token` (unique), `userId`, `expiresAt`, `ipAddress?`,
  `userAgent?`, timestamps.
- **Account** — `id`, `accountId`, `providerId`, `userId`, password hash for the
  credentials provider, OAuth token fields (unused initially), timestamps.
- **Verification** — `id`, `identifier`, `value`, `expiresAt`, timestamps. Used
  for password reset and any future email verification.

Optional, only if Better Auth is configured with database-backed rate limiting:
a **RateLimit** model generated by Better Auth. If we use in-memory/upstash-free
rate limiting, no table is needed. Decision deferred to Phase 2 after checking
the generated schema and Vercel's serverless constraints.

### 3.2 Application models

```prisma
enum SharedMapRole {
  OWNER
  MEMBER
}

model VisitedCountry {
  id             String    @id @default(cuid())
  userId         String
  countryCode    String    @db.Char(2)      // ISO 3166-1 alpha-2, uppercase
  firstVisitedAt DateTime? @db.Date         // optional, user-entered
  note           String?   @db.VarChar(280) // optional, private
  createdAt      DateTime  @default(now())
  updatedAt      DateTime  @updatedAt

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([userId, countryCode])
  @@index([countryCode])
  @@map("visited_countries")
}

model SharedMap {
  id          String   @id @default(cuid())
  name        String   @db.VarChar(80)
  description String?  @db.VarChar(280)
  ownerId     String
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  owner       User                 @relation("OwnedMaps", fields: [ownerId], references: [id], onDelete: Cascade)
  members     SharedMapMember[]
  invitations SharedMapInvitation[]

  @@index([ownerId])
  @@map("shared_maps")
}

model SharedMapMember {
  id        String        @id @default(cuid())
  mapId     String
  userId    String
  role      SharedMapRole @default(MEMBER)
  joinedAt  DateTime      @default(now())

  map  SharedMap @relation(fields: [mapId], references: [id], onDelete: Cascade)
  user User      @relation("MapMemberships", fields: [userId], references: [id], onDelete: Cascade)

  @@unique([mapId, userId])
  @@index([userId])
  @@map("shared_map_members")
}

model SharedMapInvitation {
  id           String        @id @default(cuid())
  mapId        String
  email        String        @db.VarChar(320) // lowercased, normalized
  tokenHash    String        @unique           // SHA-256 of the raw token
  role         SharedMapRole @default(MEMBER)
  invitedById  String
  expiresAt    DateTime
  acceptedAt   DateTime?
  revokedAt    DateTime?
  createdAt    DateTime      @default(now())

  map       SharedMap @relation(fields: [mapId], references: [id], onDelete: Cascade)
  invitedBy User      @relation("SentInvitations", fields: [invitedById], references: [id], onDelete: Cascade)

  @@index([mapId, email])
  @@index([expiresAt])
  @@map("shared_map_invitations")
}
```

### 3.3 Why no `Country` table

The country list is static, versioned with the code, and needed on the client
for rendering. A database copy would drift from the SVG geometry and require a
seed/migration every time the dataset changes. Instead:

- the dataset lives in `src/data/countries.ts` (generated),
- the server validates every `countryCode` against it before writing,
- removing a country from the dataset is a **data migration** concern: the
  Phase 3 generator must report orphaned visit rows rather than deleting them.

If a future feature needs per-country editorial content (translations, notes,
external links), a `CountryMeta` table can be added then; it would still be
keyed by the same alpha-2 code.

## 4. Invariants

| Invariant | Enforced by |
| --- | --- |
| One visit row per user per country | `@@unique([userId, countryCode])` |
| A map has exactly one owner | `ownerId` on `SharedMap`; the owner also has a `SharedMapMember` row with `OWNER` |
| No duplicate membership | `@@unique([mapId, userId])` |
| Invitation email is normalized | Application layer (lowercase + trim) before insert |
| Only one active invitation per (map, email) | Application layer: revoke/replace previous active invite before creating a new one |
| Expired/revoked/accepted invites cannot be used | Application layer checks all three states transactionally |
| Country code is valid | Application layer against the dataset, before insert |
| Combined map never leaks raw member visits | Query layer returns aggregates, not per-user rows, to the client |

The "owner is also a member" rule keeps authorization and the combined-view
query uniform. It is created in the same transaction as the map.

## 5. Authorization query patterns

All of these live in `src/server/authorization.ts` and are unit/integration
tested. They return `null`/throw a 404-style error when the caller is not a
member — never "403 with existence confirmed" for private maps.

```ts
// Personal map: always scoped to the session user.
prisma.visitedCountry.findMany({ where: { userId } });

// Membership check + map fetch in one query.
prisma.sharedMap.findFirst({
  where: { id: mapId, members: { some: { userId } } },
  include: { members: { include: { user: true } } },
});

// Combined view: aggregate country -> member ids, never raw notes.
prisma.visitedCountry.groupBy({
  by: ["countryCode"],
  where: { userId: { in: memberIds } },
  _count: { userId: true },
});
```

Notes and `firstVisitedAt` are private to their owner in the first release; the
combined view uses only country codes and counts. A later "show dates" feature
must be opt-in per member.

## 6. Transactions and concurrency

- **Toggle a visit** is idempotent: `upsert` on `(userId, countryCode)` for add,
  `deleteMany` for remove. Two rapid toggles must not create duplicates or 500s.
- **Accept an invitation** runs in a transaction:
  1. `SELECT ... FOR UPDATE`-equivalent by updating the invitation row only if
     `acceptedAt IS NULL AND revokedAt IS NULL AND expiresAt > now()`,
  2. verify the signed-in user's email matches,
  3. create membership (skip if already a member),
  4. stamp `acceptedAt`.
  If the update affects 0 rows, the invite is invalid/expired/already used.
- **Create map** creates the map, owner membership, and (optionally) the first
  invitations in one transaction.
- **Delete account** relies on cascades; the UI warns that owned shared maps are
  deleted for everyone. A future "transfer ownership" flow would change this.

## 7. Indexes and expected queries

| Query | Index |
| --- | --- |
| User's visits | `visited_countries(user_id)` via the unique composite's prefix |
| Combined map | `visited_countries(country_code)` + join on user ids |
| User's maps | `shared_map_members(user_id)` |
| Map members | `shared_map_members(map_id)` via unique prefix |
| Pending invites for a map | `shared_map_invitations(map_id, email)` |
| Expired invite cleanup | `shared_map_invitations(expires_at)` |
| Session lookup | `session(token)` unique |
| User by email | `user(email)` unique |

AtlasShare's data volume is small (hundreds of countries × users), so no
denormalized counters are needed. Count on read.

## 8. Migrations

- Local: `npx prisma migrate dev --name <change>`.
- CI/production: `npx prisma migrate deploy` as a release step **before** the
  new deployment serves traffic. Never `prisma db push` against production.
- Every migration is reviewed for: data loss, lock duration, default values on
  existing rows, and backward compatibility during a rolling deploy.
- Destructive changes use expand/contract (add new column, backfill, switch
  reads, drop old column in a later release).
- Migration files are committed. The database schema and the Prisma schema must
  never diverge.
- Neon PITR/branching is the recovery path; take a branch before risky
  migrations.

## 9. Seeding and test data

- No production seed. The country dataset is code, not rows.
- Integration tests create their own users/maps in a transaction or a dedicated
  test database and clean up after themselves. `TEST_DATABASE_URL` is required
  for those tests; without it they are **skipped** and reported as skipped, not
  passed.
- Never copy production data into development. If realistic data is needed,
  generate synthetic users and visits.

## 10. Retention and deletion

- Sessions: cleaned up on expiry by Better Auth / a maintenance task.
- Invitations: expired invites are inert immediately; rows are purged after 30
  days by a maintenance script (planned, Phase 4).
- Account deletion: cascades visits, memberships, owned maps, and sent
  invitations. This is irreversible and must be confirmed in the UI.
- Backups: Neon's retention window (per plan). Document the actual window when
  the project is provisioned.
