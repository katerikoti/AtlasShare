# AtlasShare — Database

Status: **implemented through Phase 6.** The auth and application tables exist
in the Phase 2 migration. Phase 3 uses `visited_countries`; Phase 4 uses the
`shared_maps`, `shared_map_members`, and `shared_map_invitations` tables created
in that same migration. Phase 5 adds insights and comparison as derived views.
Phase 6 is entirely client-side and adds no table. **Phases 4–6 added no schema
change.** One data migration,
`20261027120000_limit_to_recognized_countries`, deletes visits to the retired
country codes after the 195-country dataset revision. The schema below is the
contract later phases build on. It will be adjusted only with a documented
reason (and a migration), not silently.

## 1. Principles

1. **Postgres is the source of truth** for accounts, visits, memberships, and
   invitations. The country dataset is static application data, not a table.
2. **Every user-owned row is scoped by `userId`**, and every read/write goes
   through a server-side authorization helper. There is no "trusted client".
3. **Cascades are deliberate.** Deleting an account must remove that person's
   private data. Shared-map content owned by that person is deleted with it.
4. **Invitation tokens are stored hashed.** Better Auth's password-reset token is
   the documented exception: version 1.7.12 stores it in
   `verification.identifier` as `reset-password:<token>`. It is single-use and
   expires in one hour; a custom reset flow is required to hash it. Invitation
   tokens and other application secrets never appear in plaintext.
5. **Timestamps are UTC** (`timestamptz`), generated by the database or Prisma,
   never by the client.
6. **Country codes are ISO 3166-1 alpha-2**, uppercase, two characters, and
   validated against the committed dataset before insert.

## 2. Connection model

Neon provides two connection strings in production:

- `DATABASE_URL` — **pooled** connection, used by the app at runtime.
- `DIRECT_URL` — **direct** connection, used only for migrations and
  introspection.

Prisma 7 is ESM and configured through `prisma.config.ts`; the CLI reads
`DIRECT_URL` when set, the runtime client uses `DATABASE_URL` through a driver
adapter. Never point `TEST_DATABASE_URL` at production.

Local development uses Homebrew PostgreSQL 18 with two databases:
`atlasshare_dev` (manual checks) and `atlasshare_test` (migration/test work).
The runtime adapter is selected by host in `src/server/db.ts`:

- `*.neon.tech` → `@prisma/adapter-neon`;
- anything else → `@prisma/adapter-pg`.

This keeps local development on plain Postgres while production uses Neon. Both
paths are exercised only locally so far; Neon itself is still unprovisioned.
`DIRECT_URL` is optional in `.env` for `prisma generate`, but migration commands
need it (or `DATABASE_URL`) set to a real database.

## 3. Schema (implemented in migration `20261025141145_init_auth_and_accounts`)

The schema was generated for Better Auth with the installed CLI, then extended
with the application models below. Better Auth's generated fields are the source
of truth for its own tables — do not hand-edit them to "tidy" them.

### 3.1 Better Auth tables

Standard Better Auth Prisma models. Table names are singular lowercase via
Prisma `@@map`: `user`, `session`, `account`, `verification`.

- **User** — `id`, `name`, `email` (unique), `emailVerified`, `image`,
  `createdAt`, `updatedAt`, plus the AtlasShare additional field:
  - `welcomeEmailSentAt DateTime?` — records a successful welcome send; null
    means not sent (or email was not configured).
- **Session** — `id`, `token` (unique), `userId`, `expiresAt`, `ipAddress?`,
  `userAgent?`, timestamps.
- **Account** — `id`, `accountId`, `providerId`, `userId`, password hash for the
  credentials provider, OAuth token fields (unused initially), timestamps.
- **Verification** — `id`, `identifier`, `value`, `expiresAt`, timestamps. Used
  for password reset and, since ADR-036, for email-verification codes: the row's
  `identifier` is `email-verification-otp-<email>` and `value` is
  `<hash of the 6-digit code>:<attempts used>` (the code itself is never
  stored). A code row is replaced by a new one and removed once the code is used;
  a never-verified account's row is also removed if a new sign-up replaces that
  account. **Known deviation:** the password-reset token is part of `identifier`
  rather than hashed (see principle 4).
- `User.emailVerified` is now enforced: it is `false` until the code is entered,
  and sign-in is refused while it is `false`. The accounts that existed before
  this change were set to `true` once with a one-off `UPDATE "user" SET
  "emailVerified" = true WHERE "emailVerified" = false` on the development
  database (2 rows). It is deliberately not a migration; do not run it after
  launch, since it would verify real unverified accounts.

No **RateLimit** table exists. Rate limiting is Better Auth's in-memory limiter,
production-only. This is documented as an accepted limitation in `SECURITY.md`.

### 3.2 Application models

```prisma
enum SharedMapRole {
  OWNER
  MEMBER
}

model VisitedCountry {
  id             String    @id @default(cuid())
  userId         String
  countryCode    String    @db.Char(2)      // ISO 3166-1 alpha-2, uppercase
  firstVisitedAt DateTime? @db.Date         // reserved; not exposed (D2)
  note           String?   @db.VarChar(280) // reserved; not exposed (D2)
  createdAt      DateTime  @default(now())
  updatedAt      DateTime  @updatedAt

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([userId, countryCode])
  @@index([countryCode])
  @@map("visited_countries")
}

model SharedMap {
  id          String   @id @default(cuid())
  name        String   @db.VarChar(80)
  description String?  @db.VarChar(280)
  ownerId     String
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  owner       User                 @relation("OwnedMaps", fields: [ownerId], references: [id], onDelete: Cascade)
  members     SharedMapMember[]
  invitations SharedMapInvitation[]

  @@index([ownerId])
  @@map("shared_maps")
}

model SharedMapMember {
  id        String        @id @default(cuid())
  mapId     String
  userId    String
  role      SharedMapRole @default(MEMBER)
  joinedAt  DateTime      @default(now())

  map  SharedMap @relation(fields: [mapId], references: [id], onDelete: Cascade)
  user User      @relation("MapMemberships", fields: [userId], references: [id], onDelete: Cascade)

  @@unique([mapId, userId])
  @@index([userId])
  @@map("shared_map_members")
}

model SharedMapInvitation {
  id           String        @id @default(cuid())
  mapId        String
  email        String        @db.VarChar(320) // lowercased, normalized
  tokenHash    String        @unique           // SHA-256 of the raw token
  role         SharedMapRole @default(MEMBER)
  invitedById  String
  expiresAt    DateTime
  acceptedAt   DateTime?
  revokedAt    DateTime?
  createdAt    DateTime      @default(now())

  map       SharedMap @relation(fields: [mapId], references: [id], onDelete: Cascade)
  invitedBy User      @relation("SentInvitations", fields: [invitedById], references: [id], onDelete: Cascade)

  @@index([mapId, email])
  @@index([expiresAt])
  @@map("shared_map_invitations")
}
```

### 3.3 Why no `Country` table

The country list is static, versioned with the code, and needed on the client
for rendering. A database copy would drift from the SVG geometry and require a
seed/migration every time the dataset changes. Instead:

- the canonical codes/names live in `src/data/countries.generated.ts`, imported
  through the `src/data/countries.ts` helper; the continent assignment lives in
  `src/data/country-regions.ts` and is attached by that helper; generated SVG
  geometry lives in `public/map/countries.json`;
- the server validates every `countryCode` against the helper before writing;
- region statistics are computed from visits plus this static mapping at read
  time, never stored as rows;
- the generator is deliberately database-free and never deletes visit rows. If a
  dataset change removes a code, that change needs a **data migration**. The
  195-country revision followed that rule: the migration deletes visits whose
  code is outside the new 195-code set, and the server read boundary also drops
  unknown codes so a stale row cannot inflate a count. Review the affected row
  count before applying a similar migration in production.

If a future feature needs per-country editorial content (translations, notes,
external links), a `CountryMeta` table can be added then; it would still be
keyed by the same alpha-2 code.

## 4. Invariants

| Invariant | Enforced by |
| --- | --- |
| One visit row per user per country | `@@unique([userId, countryCode])` |
| A map has exactly one owner | `ownerId` on `SharedMap`; the owner also has a `SharedMapMember` row with `OWNER` |
| No duplicate membership | `@@unique([mapId, userId])` |
| Invitation email is normalized | Application layer (lowercase + trim) before insert |
| Only one active invitation per (map, email) | Application layer: revoke/replace previous active invite before creating a new one |
| Expired/revoked/accepted invites cannot be used | Application layer checks all three states transactionally |
| Country code is valid | Application layer against the dataset, before insert |
| Every country code has exactly one region | Static dataset + test over all 195 countries |
| Region counts sum to the headline visited total | Pure `getRegionBreakdown` function + test |
| Combined map never leaks raw member visits | Query layer returns aggregates, not per-user rows, to the client |
| Shared comparison adds no new private data | Derived client-side from the authorized combined counts and the current member's codes |

The "owner is also a member" rule keeps authorization and the combined-view
query uniform. It is created in the same transaction as the map.

## 5. Authorization query patterns

All of these live in `src/server/authorization.ts` and are unit/integration
tested. They return `null`/throw a 404-style error when the caller is not a
member — never "403 with existence confirmed" for private maps.

```ts
// Personal map: always scoped to the session user.
prisma.visitedCountry.findMany({ where: { userId } });

// Membership check + map fetch in one query.
prisma.sharedMap.findFirst({
  where: { id: mapId, members: { some: { userId } } },
  include: { members: { include: { user: true } } },
});

// Combined view: country -> count, plus membership/display-name rows.
// Raw visit rows, emails, and user ids are never serialized to the client.
prisma.visitedCountry.groupBy({
  by: ["countryCode"],
  where: { userId: { in: memberIds } },
  _count: { userId: true },
});
```

The rendered shared view also needs each member's deduplicated country-code set
and display name for the per-member filter. `src/server/shared-maps.ts` builds
that view from authorization-scoped membership and visit queries; it does not
send emails, user ids, notes, or dates.

`note` and `firstVisitedAt` are reserved but unused in the approved initial
scope (D2); no API or UI exposes them. Reintroducing either needs a new scope
decision; visit dates would also need a separate visit-history model for repeat
visits.

## 6. Transactions and concurrency

- **Toggle a visit** is idempotent: `upsert` on `(userId, countryCode)` for add,
  `deleteMany` for remove. Two rapid toggles must not create duplicates or 500s.
- **Accept an invitation** runs in a transaction:
  1. `SELECT ... FOR UPDATE`-equivalent by updating the invitation row only if
     `acceptedAt IS NULL AND revokedAt IS NULL AND expiresAt > now()`,
  2. verify the signed-in user's email matches,
  3. create membership (skip if already a member),
  4. stamp `acceptedAt`.
  If the update affects 0 rows, the invite is invalid/expired/already used.
- **Create map** creates the map, owner membership, and (optionally) the first
  invitations in one transaction.
- **Delete account** relies on cascades; the UI warns that owned shared maps are
  deleted for everyone. A future "transfer ownership" flow would change this.

## 7. Indexes and expected queries

| Query | Index |
| --- | --- |
| User's visits | `visited_countries(user_id)` via the unique composite's prefix |
| Combined map | `visited_countries(country_code)` + join on user ids |
| User's maps | `shared_map_members(user_id)` |
| Map members | `shared_map_members(map_id)` via unique prefix |
| Pending invites for a map | `shared_map_invitations(map_id, email)` |
| Expired invite cleanup | `shared_map_invitations(expires_at)` |
| Session lookup | `session(token)` unique |
| User by email | `user(email)` unique |

AtlasShare's data volume is small (hundreds of countries × users), so no
denormalized counters are needed. Count on read.

## 8. Migrations

- First migration: `prisma/migrations/20261025141145_init_auth_and_accounts`
  (auth tables + `visited_countries` + shared-map tables). Generated with
  `prisma migrate dev` against local `atlasshare_dev`.
- Verified on 2026-10-25 by recreating `atlasshare_test` and running
  `prisma migrate deploy` with `DATABASE_URL`/`DIRECT_URL` pointed at it: the
  migration applied cleanly and all tables were created.
- Local: `npx prisma migrate dev --name <change>`.
- CI/production: `npx prisma migrate deploy` as a release step **before** the
  new deployment serves traffic. Never `prisma db push` against production.
- Every migration is reviewed for: data loss, lock duration, default values on
  existing rows, and backward compatibility during a rolling deploy.
- Destructive changes use expand/contract (add new column, backfill, switch
  reads, drop old column in a later release).
- Migration files are committed. The database schema and the Prisma schema must
  never diverge.
- Phase 4 did not add a migration: its tables/indexes were already in
  `20261025141145_init_auth_and_accounts`. No database reset or `db push` was
  used for Phase 4 QA.
- Neon PITR/branching is the recovery path; take a branch before risky
  migrations.

## 9. Seeding and test data

- No production seed. The country dataset is code, not rows.
- Local development and manual verification use `atlasshare_dev` with unique
  `example.com` accounts. `atlasshare_test` is used by the integration run.
- Integration tests create their own users/maps in a dedicated test database and
  clean up after themselves. Vitest loads `.env` and runs the persistence suite
  when `TEST_DATABASE_URL` is set; without it, the suite is skipped with a clear
  reason. The test database name is `atlasshare_test`.
- Never copy production data into development. If realistic data is needed,
  generate synthetic users and visits.

## 10. Retention and deletion

- Sessions: cleaned up on expiry by Better Auth / a maintenance task.
- Invitations: expired invites are inert immediately; rows are purged after 30
  days by a maintenance script (**not yet implemented**; deferred to Phase 8 or
  a deployment task). There is no cron/queue in the app.
- Account deletion: cascades visits, memberships, owned maps, and sent
  invitations. This is irreversible and must be confirmed in the UI.
- Backups: Neon's retention window (per plan). Document the actual window when
  the project is provisioned.

   from the signed-in user's already-authorized visit codes and public geometry.

   `migrate deploy` to the Neon development database and the local test database.
3. The migration deletes every `visited_countries` row whose code is not in the
   canonical 195. Unknown codes are also filtered at read time, so old rows
   cannot reach the map or the export.

   application data and all counts are derived from existing visit rows.
2. Region counts and the shared comparison are pure functions tested without a
   database; the authorized shared view already carried the inputs. The personal
   country list keeps local search/order and adds no query.
3. Region counts are asserted to sum to the headline visited count, and the
   comparison is asserted to expose only codes/counts.

Resolved in Phase 4:

1. No schema change or migration was needed; the Phase 2 shared-map tables and
   indexes are sufficient.

   cover visits plus shared-map counts, privacy shape, invitations, concurrency,
   membership removal/leaving, and owner invariants.
3. Acceptance is atomic: a conditional update claims an unexpired,
   unrevoked/unaccepted invitation, then membership is created and `acceptedAt`
