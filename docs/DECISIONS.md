# AtlasShare — Decision Log (ADRs)

Format: context → decision → consequences. Status is `accepted`, `proposed`, or
`superseded`. A significant decision made during a phase must be added here
before the phase is reported complete.

---

## ADR-001 — Next.js 16 App Router with Turbopack

**Status:** accepted (Phase 1)

**Context:** The app needs SSR, server-side authorization, route-level code
splitting, and a mature deployment story. The scaffold should not fight the
framework's current defaults.

**Decision:** Next.js 16.4.3, App Router, React 19.3.0, TypeScript strict,
Turbopack for dev and build (the create-next-app default). Server Components by
default; Client Components only where interaction requires them.

**Consequences:** Server Actions and RSC keep private data on the server. Next 16
renamed Middleware to Proxy and changed caching defaults; documentation must be
read from the installed version, not from memory. Upgrading major versions is a
deliberate, tested task.

---

## ADR-002 — Tailwind CSS v4 with CSS-first design tokens

**Status:** accepted (Phase 1)

**Context:** The palette is small and must stay consistent across UI, email, and
export. Tailwind v3 config files add a second source of truth.

**Decision:** Tailwind 4.3.3, configured through `@theme` in
`src/app/globals.css`. CSS custom properties are the source of truth for screen
colors; `src/config/brand.ts` mirrors them for canvas/email use. A unit test
checks contrast.

**Consequences:** No `tailwind.config.ts`. Renaming a color means updating both
the CSS tokens and the brand mirror; the test catches drift in the values it
checks. Arbitrary color literals in components are discouraged.

---

## ADR-003 — Cache Components disabled

**Status:** accepted (Phase 1)

**Context:** Next 16 can cache and partially prerender aggressively. AtlasShare
is authenticated and nearly every screen depends on the current user. Accidental
caching of private data is a serious risk.

**Decision:** `cacheComponents` and partial prefetching remain off. Default to
dynamic, request-time rendering. Any caching is explicit, scoped to public data,
and tested for cross-user leakage.

**Consequences:** Slightly more server work per request; a simpler privacy
model. Enabling Cache Components later requires Suspense boundaries around every
session read and a privacy review.

---

## ADR-004 — Better Auth for authentication

**Status:** accepted (Phase 1)

**Context:** Auth.js v5 was still beta at decision time; Better Auth supports
Next 16 and Prisma 7 with database sessions and a first-party Prisma adapter.

**Decision:** Better Auth 1.7.12, email/password first, database sessions,
Prisma adapter. OAuth may be added later.

**Consequences:** Auth tables are generated by Better Auth and must match its
expected schema. We own the UX pages. Session validation happens server-side in
the data layer; the proxy is only an optimistic redirect. Upgrading Better Auth
can require schema migrations.

---

## ADR-005 — Prisma 7 + Neon driver adapter, ESM

**Status:** accepted (Phase 1)

**Context:** Neon is the chosen Postgres host; Prisma 7 requires/encourages
driver adapters and uses `prisma.config.ts`.

**Decision:** Prisma 7.10.1 with `@prisma/adapter-neon`, ESM, pooled
`DATABASE_URL` at runtime and direct `DIRECT_URL` for migrations. Migrations are
committed and applied with `migrate deploy` in release.

**Consequences:** Two connection strings must be configured correctly. `db push`
is banned in production. The app must run on the Node runtime (not Edge) where
the adapter and Prisma engine are supported.

---

## ADR-006 — Resend for transactional email, plain HTML templates

**Status:** superseded by ADR-023 (Phase 2)

**Context:** Needed: welcome, password reset, invitations. React Email adds a
build/render dependency; the emails are simple.

**Decision:** Resend 6.34.1 via a thin server wrapper. Plain HTML strings with
inline styles derived from the brand palette. Sending is best-effort; failures
never roll back the underlying action.

**Consequences:** No component reuse between app and email; templates are small
and reviewed manually. A verified domain (SPF/DKIM) is required before
production sending. No tracking pixels.

## ADR-007 — Custom SVG map, no runtime geo library

**Status:** accepted (Phase 1)

**Context:** The product is country-level. Map libraries (Leaflet/MapLibre) bring
tiles, projections, and a heavier client for no benefit. A designed SVG fits the
brand and the export.

**Decision:** A hand-built React SVG map from a committed, generated dataset.
CSS-driven fills, a parallel accessible country list, no runtime geo dependency.

**Consequences:** We own projection/geometry generation (offline script) and
must curate disputed territories. Bundle size is controlled and the export is
trivial to render from the same data. Pan/zoom, if needed, is custom.

## ADR-008 — Country dataset is static, not a database table

**Status:** accepted (Phase 1)

**Context:** The country list is the same for every user, needs to be on the
client for rendering, and changes rarely.

**Decision:** Commit a generated dataset (codes, names, region, SVG path) and
validate visit codes against it server-side. No `Country` table.

**Consequences:** No seed step; dataset changes are code changes with tests.
Removing a country requires a data-migration plan for orphaned visits. If
per-country editorial content is ever needed, add a `CountryMeta` table keyed by
the same code.

---

## ADR-009 — ISO 3166-1 alpha-2 identifiers, Kosovo as `XK`

**Status:** accepted (Phase 1)

**Context:** Display names are ambiguous and change; SVG ids from libraries vary.

**Decision:** Store uppercase alpha-2 codes. The single documented exception is
Kosovo, stored as `XK`. Every code must exist in the committed dataset.

**Consequences:** Integrations and exports use stable codes. `XK` is not an
official ISO assignment but is widely used; document it anywhere codes are
explained. Never store names as keys.

## ADR-010 — Country set: 250 countries & territories

**Status:** accepted (2026-10-26)

**Context:** 195 sovereign states is tidy but makes common travel destinations
(Hong Kong, Greenland, Puerto Rico, Réunion, Curaçao) unmarkable. 249 ISO
3166-1 entries + Kosovo = 250 covers what travellers actually visit but is not
"195 countries".

**Decision:** Use 250 units, label the feature "countries & territories"
consistently, count territories separately, and include Kosovo as `XK`.
Palestine (`PS`) and Israel (`IL`) are both separate map units; neither is
merged into the other. This is a comprehensive dataset, not a political
endorsement.

**Consequences:** The dataset, count copy, export, and tests depend on this.
Switching later is a data migration plus a copy change. Natural Earth's default
grouping of Palestine under Israel is unacceptable; the Phase 3 generator must
verify separate `PS` and `IL` paths and labels.

## ADR-011 — Client-side SVG → canvas PNG export, no headless browser

**Status:** accepted (Phase 1)

**Context:** Users want a shareable image. Server-side rendering needs a headless
browser, extra infrastructure, and a second authorization surface.

**Decision:** A dedicated export SVG component renders the signed-in user's own
data, is serialized and drawn to a canvas at 2×–3×, and is exported as PNG with
Web Share/download fallbacks. No remote fonts/images.

**Consequences:** Export quality depends on the browser canvas (cap dimensions
for Safari). The export component's props are deliberately minimal so shared-map
or account data cannot leak in. SVG fallback covers canvas failures.

---

## ADR-012 — Invitation tokens hashed at rest, per-email, single-use

**Status:** accepted (Phase 1, implemented Phase 4)

**Context:** Invitation links grant access to other people's travel data.

**Decision:** 32 random bytes, base64url in the link, SHA-256 hash in the
database, 7-day expiry, single-use atomic acceptance, revocable, email must
match the signed-in account. Generic errors for invalid/expired/used.

**Consequences:** A database leak does not expose usable invite links. Support
cannot "look up" a token, only re-issue. Forwarded links fail for other emails,
which is intentional.

---

## ADR-013 — Two roles: OWNER and MEMBER

**Status:** accepted (Phase 1, implemented Phase 4)

**Context:** Editors/viewers sound flexible but multiply authorization checks
and UI states before the product has validated the core loop.

**Decision:** `OWNER` and `MEMBER`. Owner manages the map, invitations, and
membership. Members see the combined view and manage their own visits.

**Consequences:** Simple, testable rules. Adding roles later requires a migration
and an audit of every check. No public/anon access in the first release.

## ADR-014 — Vitest + React Testing Library; Playwright deferred

**Status:** accepted (Phase 1)

**Context:** Unit/component tests are needed immediately; end-to-end tests need
a real database and deployment target.

**Decision:** Vitest 5 + RTL + jsdom + jest-dom for unit/component tests.
Integration tests run against `TEST_DATABASE_URL` when available (skipped
otherwise, and reported as skipped). Playwright is introduced in Phase 8 (or
earlier if a phase needs browser-level verification) rather than now.

**Consequences:** Fast local feedback. No browser-level regression net until
Phase 8; until then, manual smoke tests are documented honestly. Skipped tests
are never reported as passing.

## ADR-015 — Brand identity centralized in `src/config/brand.ts`

**Status:** accepted (Phase 1)

**Context:** The product name appears in metadata, emails, exports, and UI. Hard-
coding it makes a rename error-prone.

**Decision:** `brand` is the single source for name, tagline, description,
palette mirror, and repository URL. UI reads `brand.name`.

**Consequences:** A rename is a small, reviewable change. The palette is
duplicated in CSS (source of truth for rendering) and `brand.ts` (non-CSS use);
tests check contrast, and reviewers must keep the two lists in sync.

## ADR-016 — `proxy.ts` for optimistic redirects only

**Status:** accepted (Phase 1, implemented Phase 2)

**Context:** Next 16 renamed Middleware to Proxy. It is tempting to enforce auth
there, but it runs before request resolution and cannot safely do DB-backed
authorization.

**Decision:** `proxy.ts` may check for a session cookie and redirect for UX. Every
private read/write re-checks the session and membership in the server layer.

**Consequences:** Slightly more code in data-access helpers; correct security.
Tests target the data layer, not the proxy.

## ADR-017 — Local PostgreSQL for development; adapter selected by host

**Status:** accepted (Phase 2)

**Context:** Neon was not provisioned, but Phase 2 needed a real database,
migrations, and repeatable manual checks. Requiring a cloud branch for every
local test would slow development.

**Decision:** Use Homebrew PostgreSQL 18 locally (`atlasshare_dev`,
`atlasshare_test`). Keep Neon as the production target. `src/server/db.ts`
selects `@prisma/adapter-neon` for `*.neon.tech` hosts and `@prisma/adapter-pg`
for everything else. Both adapters are pinned at 7.10.1.

**Consequences:** Local development has no pooling/SSL parity with Neon, so the
Neon path must be exercised before deployment. Two adapters are shipped; the
selection is one small, tested code path. Credentials stay in `.env`.

## ADR-018 — Lazy environment, database, and auth initialization

**Status:** accepted (Phase 2)

**Context:** `next build` evaluates route modules. Eagerly constructing Better
Auth or Prisma at module scope would require database and auth secrets during a
build that should not need them.

**Decision:** `getEnv()`, `getDb()`, and `getAuth()` validate/construct lazily on
first use. Importing modules never throws. Env validation reports the offending
variable names. Test helpers reset memoized env/mailer state.

**Consequences:** Builds work without runtime secrets; misconfiguration fails at
the first request rather than at build time. Developers must not accidentally
eagerly initialize these modules at import time in future code.

---

## ADR-019 — Password, session, and rate-limit policy

**Status:** accepted (Phase 2)

**Context:** The product needs a usable policy on phones without weakening the
basic account-takeover defenses.

**Decision:** Passwords 12–128 characters (scrypt via Better Auth). Sessions last
30 days with a one-day rolling update and no session cookie cache. Rate limits
use Better Auth's in-memory limiter, enabled only in production: sign-in
10/15 min, sign-up 5/hour, reset request 3/hour, reset submit 10/15 min.

**Consequences:** Long passphrases are encouraged; no breached-password list yet.
Revocation is immediate because sessions are not cached in a cookie. Per-instance
memory is only a speed bump on serverless; a shared limiter is future work.
Limits are not active in development, so tests do not lock themselves out.

## ADR-020 — Password change signs out everywhere

**Status:** accepted (Phase 2)

**Context:** Better Auth rotates the current session when the password changes.
The original proxy redirected signed-in users away from auth pages based on cookie
presence. During verification this raced the rotation and produced an
`/account` ↔ `/sign-in` redirect loop that blanked the client.

**Decision:** After a successful password change, delete every session for the
user (including the rotated one), redirect to
`/sign-in?passwordChanged=1`, and show a notice. The proxy only protects
`/account`; it never redirects a signed-in user away from sign-in.

**Consequences:** Users must sign in again after changing a password. Other
devices are guaranteed to be signed out. The redirect loop is gone. Auth pages
remain reachable while signed in, which is acceptable and avoids cookie-race
redirects.

## ADR-021 — Better Auth's raw password-reset token storage accepted for now

**Status:** accepted (Phase 2, known deviation)

**Context:** Better Auth 1.7.12 stores password-reset tokens in
`verification.identifier` as `reset-password:<token>`. Our general policy says
tokens are hashed at rest. A custom reset flow would be needed to hash them.

**Decision:** Accept the library behavior for Phase 2. Tokens are single-use,
expire after one hour, and revoke sessions on use. Document the deviation in
`SECURITY.md` and `DATABASE.md`.

**Consequences:** Anyone with database read access could use a live reset token
within its short window. Risk is bounded but real. Revisit before public launch
or replace with a custom hashed-token flow.

## ADR-022 — Welcome email is best-effort and sent at most once

**Status:** accepted (Phase 2)

**Context:** Sign-up must not fail because Brevo is down or unconfigured. The
welcome message is a courtesy, not a verification step.

**Decision:** After user creation, claim the user with `welcomeEmailSentAt`; send
if the mailer is configured; release the claim on failure or no-op. Never block
sign-up. No retry queue or background job in Phase 2.

**Consequences:** Duplicate welcomes are prevented. Users who sign up while email
is disabled will not receive a welcome later unless a retry mechanism is added.
A verified Brevo sender is required for email delivery; an authenticated domain
is still recommended for production deliverability.

## ADR-023 — Brevo replaces Resend for transactional email

**Status:** accepted (Phase 2)

**Context:** The project needs real welcome and password-reset emails without
buying a domain. Resend requires a verified domain (or its onboarding sender,
which only delivers to the account owner). Brevo's free plan allows 300 emails
per day and can send from a verified individual address, which is enough for
practice and early testing.

**Decision:** Use Brevo's transactional HTTP API (`POST
https://api.brevo.com/v3/smtp/email`) through a small `fetch`-based mailer in
`src/server/email/mailer.ts`. No Brevo SDK or email rendering dependency.
`BREVO_API_KEY` is optional; without it the no-op mailer logs and skips. The
`EMAIL_FROM` value may be `Name <verified@example.com>`; the address must be a
verified Brevo sender.

**Consequences:** No domain purchase is needed to test real delivery. Brevo may
rewrite or annotate mail from an unauthenticated domain (notably to Gmail,
Yahoo, and Microsoft recipients), so production should authenticate a domain for
reliable sender identity and deliverability. The provider receives the recipient
address and message content. The app adds no tracking pixels, but Brevo records
delivery/open telemetry and injects a `List-Unsubscribe` header into
transactional email, so Gmail may show its own unsubscribe control even when the
body has no unsubscribe link. Brevo's free plan does not let you replace that
header (Enterprise can request `List-Help` for eligible transactional mail);
clicking it can suppress future transactional email. Resend is removed from the
dependency tree. Brevo's optional IP allowlisting can block local or serverless
callers; Vercel's dynamic egress requires disabling it for the production key,
using static egress, or moving to a scoped M2M bearer token.

## ADR-024 — Visited state only; no notes or visit dates

**Status:** accepted (2026-10-26)

**Context:** D2 asked whether optional per-country notes and first-visited dates
belong in Phase 3 or Phase 5. The product owner does not need notes and does not
want visit dates; repeat visits would also require a multi-visit history rather
than a single date.

**Decision:** The initial product stores only whether a country is visited. Do
not build notes, visit dates, or visit-history UI. The optional
`visited_countries.note` and `firstVisitedAt` columns remain reserved but unused;
they are not exposed by any API or UI.

**Consequences:** Phase 3 stays small and the map/count loop is the focus.
Reintroducing notes or dates needs a new scope decision; dates specifically need
a separate visit-history model so multiple visits are represented honestly.
Shared maps never expose any note/date data because none is stored through the
app.

## ADR-025 — Curated `@svg-maps/world` plus a custom Antarctica outline

**Status:** accepted (Phase 3)

**Context:** The map needs 250 recognizable units, including separate Palestine
and Israel paths, small territories, and Antarctica. The Phase 1 plan named
Natural Earth 1:50m, but that dataset groups Palestine under Israel and misses
small states. A Natural Earth 1:10m extraction was also not a clean 250-code
base in testing (258 features, 239 valid unique codes, 11 required codes
missing). `@svg-maps/world` already provides separate `PS`/`IL` paths and useful
coverage.

**Decision:** Generate the dataset from the exact `@svg-maps/world@2.0.0`
package (CC-BY-4.0), remove the non-ISO `go`/`ju` paths, merge the six `um-*`
subdivisions into one `UM` path, add `AQ` from a committed Natural Earth 1:10m
outline (public domain), normalize names, sort by code, and assert 250 units.
Write both `src/data/countries.generated.ts` and `public/map/countries.json`
deterministically; commit both. The generator fails if the installed package
version differs. Attribute the source and Antarctica outline in the map and
repository docs.

**Consequences:** The map does not depend on a runtime geo package. The
curation is explicit and reproducible. The base geometry's projection and
simplification are retained, and the custom Antarctica outline is approximate.
Updating the source package requires regenerating, reviewing the output diff,
and checking any removed codes for orphaned visit rows before deployment. The
geometry asset is public, unversioned data (~1.2 MB raw, ~400 KB compressed
locally) served with ETag revalidation.

## ADR-026 — Explicit-membership shared maps expose member names and country sets

**Status:** accepted (Phase 4)

**Context:** The Phase 4 plan said the aggregation should expose only country
codes and counts, but the member filter needs a stable way to list and identify
members. Email addresses and user ids are unnecessary and more sensitive.
Sending only a combined set would make per-member filtering impossible.

**Decision:** Shared maps remain explicit-membership only. Every member can see
other members' display names, membership ids, and deduplicated visited-country
sets so the filter can work. The client receives combined counts and no emails,
user ids, raw visit rows, notes, or visit dates. Pending invitation emails are
returned only to the owner. The account page warns that the display name appears
on shared maps.

**Consequences:** Members learn each other's country-level travel marks, which
is the product's intended shared value. A person who needs to hide their name
must change their display name before joining. Adding nicknames or per-map
aliases later is a schema/UI change. Tests assert the DTO shape and the
owner-only invitation query.

## ADR-027 — Shared maps are read-only; the owner cannot leave

**Status:** accepted (Phase 4)

**Context:** Letting members mark countries inside a shared map would blur
ownership and risk changing a person's private map accidentally. Removing the
owner would leave a map without the required single owner.

**Decision:** The shared page is read-only for everyone, including the owner.
Members change visits only on `/map`. The owner can update details, invite,
revoke, remove members, and delete the map; the owner cannot leave. Members can
leave. Removing or leaving deletes only membership, never the person's private
visits. Deletion requires typing `DELETE`.

**Consequences:** Clear authorization and no accidental edits. A shared view
reflects changes on the next request; there is no real-time sync. Transferring
ownership is not implemented, so an owner who wants out must delete the map or
an ownership-transfer flow must be added later.

## ADR-028 — Invitation acceptance matches an unverified account email

**Status:** accepted (Phase 4, revisit before launch)

**Context:** Invitations are addressed to an email and must not be redeemable by
a different account. Better Auth email verification is not enforced in this
project, so the strongest available check is a normalized string match between
the signed-in account email and the invitation email.

**Decision:** Accept only when the signed-in account email matches the
invitation email, and perform the claim atomically. Do not add a verification
gate in Phase 4 because there is no verification UI/flow yet. Record the
limitation instead of claiming that an invitation proves address control.

**Consequences:** A different signed-in email is rejected. A forwarded link can
still be redeemed by someone who registers the unregistered invited address
first. Requiring verified email before acceptance is a pre-launch hardening
task; adding it needs a verification flow but no schema change. Invitations
remain single-use, 7-day, hashed, revocable, and high-entropy.

## ADR-029 — Continent-level region is static dataset metadata

**Status:** accepted (Phase 5)

**Context:** Phase 5 needs region counts that sum to the visited total. The
generated dataset carried only codes and names, and the geometry generator
should stay deterministic and unchanged. There is no single runtime API for
continent membership, and country/territory assignment involves judgment calls
at the edges.

**Decision:** Add `src/data/country-regions.ts` as the single source of truth for
one continent-level region per unit: Africa, Americas, Asia, Europe, Oceania, or
Antarctica. It follows the United Nations M49 geoscheme at the continent level.
Russia is Europe; Türkiye, Cyprus, Armenia, Azerbaijan, Georgia, and Kazakhstan
are Asia; dependent territories follow their geographic continent. The mapping
is attached to the generated list by `src/data/countries.ts`, so consumers keep
one `countries` import and no extra country table or migration is needed.

**Consequences:** Every unit gets exactly one assignment, enforced at startup and
by a dataset test; the region totals sum to 250. Region names are display labels,
not localized. Changing the grouping is a code change plus test update, not a
data migration, because no region value is stored in Postgres. The grouping is a
travel-map aid, not a political statement.

## ADR-030 — Shared comparison is derived from the authorized aggregate view

**Status:** accepted (Phase 5)

**Context:** The Phase 5 scope allows a shared comparison ("visited by
everyone", "only you", "not yet by anyone") only if privacy allows. The Phase 4
shared view already sends each member's display name and deduplicated country
codes for the per-member filter, plus aggregate per-country counts. A new
server endpoint would add attack surface and a second authorization path for no
new product data.

**Decision:** Compute the comparison in the browser from the already-authorized
view. "Visited by everyone" means a combined count equal to the member count;
"only you" means a code in the signed-in member's set whose combined count is
one; "not yet by anyone" means the static dataset minus the combined codes. Send
no additional identity fields, raw visit rows, notes, dates, emails, or user ids.

**Consequences:** The comparison exposes only country codes and counts, and no
member learns anything the member filter did not already reveal. There is no new
query or migration and the data layer stays unchanged. If the shared view ever
stops sending per-member country sets, the comparison must move server-side or
be removed. The UI must not imply real-time updates; it reflects the loaded
request.

## ADR-031 — Personal country list stays search-only

**Status:** accepted (owner review, 2026-10-27)

**Context:** The initial Phase 5 personal map added visited/region filters and
sort controls. Owner review found the result too complicated and asked for the
prior simple list: one search field, the alphabetical scrollable list, and a
checkbox on the right. The owner also asked to remove the map legend and the
visual-aid note, and to show checked state by colouring the country name and
checkbox.

**Decision:** Remove the personal visited/region/sort controls, reset action, and
result count. Keep local search by name or code, the alphabetical 250-row
checklist, and the transient saving state. A checked country name and its
checkbox use dusty rose; there is no separate "visited"/"not visited" row text.
Remove the map legend and explanatory note. Keep the continent progress bars and
the shared comparison unchanged.

**Consequences:** The personal list is simpler and closer to the Phase 3 design,
at the cost of not being able to isolate visited or regional rows. Search state
still lasts only for the mounted view. The filtering/sorting helpers and their
tests were removed; `country-insights.ts` now covers region counts and shared
comparison only. This is a product-design decision, not a privacy or data change.
